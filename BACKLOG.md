## ✅ Recently Completed

- **Amex BBP missing from Portfolio/ecosystem drill-down + `earn-summary`/`earn-detail` totals diverging (2026-07-19)** — User reported "Amex Blue Business Plus 1008" missing from the Amex MR ecosystem drill-down (it did show in the Your Cards strip, just not attributed to any ecosystem). Root cause: account 135 had `product_id`/`ecosystem_id` both `NULL` — never linked to a `CardProduct`, so every ecosystem-attribution query silently excluded it. The correct catalog product already existed (`amex_blue_business_plus`, id 32) but the auto-suggestion banner had proposed the wrong one ("Amex Platinum", medium confidence) — see B10. Linked account 135 → product 32 via the existing `/api/accounts/{id}/link-product` endpoint. While verifying, found a second bug: `/api/cards/earn-summary` (powers the Portfolio tiles) and `/api/ecosystems/{id}/earn-detail` (powers the drill-down) disagreed on point totals for the same account/period — e.g. Amex BBP showed +1,524 pts on the Portfolio tile vs -146 pts on the drill-down. Cause: `earn-summary` used a flat SQL `SUM(amount)` aggregate with its own hand-rolled Expense/Income filter, never migrated to `compute_points_earn()` (the single authoritative per-transaction function, with Amex per-dollar rounding, `points_earn_override`, and payment-description detection already fixed there in earlier sessions). Rewrote `earn-summary`'s non-`auto_top_category` path to fetch transaction rows and call `compute_points_earn()` per-row, matching `earn-detail` exactly — verified byte-for-byte agreement across all 9 ecosystems (Amex MR, Marriott Bonvoy, Chase UR, etc.) after the fix. Deliberately left the `auto_top_category` branch (Citi Custom Cash-style 5%-on-top-category cards) untouched, since `earn-detail` doesn't have an equivalent calculation to match against — logged as B11.
- **Classification-engine consolidation (deployed 2026-07-18, 8-commit sequence)** — Redesign of transaction auto-classification, planned at `/Users/omermorashti/.claude/plans/shiny-zooming-conway.md`. Goal: every classification traceable to one specific active `CategorizationRule` or sitting in the review queue — nothing silently inferred with no visible trace, the architecture class that caused the Best Buy regression (see B6 below). Shipped in dependency order, each step verified against live production data before the next:
  1. Deleted the dead `MerchantOverride` table/endpoints (0 rows, unreachable from any UI — confirmed before removing).
  2. Deleted `learn_from_corrections()`/`_check_transfer_correction()` entirely (not just patched). Ran a read-only diff first: 97 transactions depended on them — reviewed each merchant with the user and created 5 explicit rules to replace the inference before deleting it (Pruplazacafe, Stop & Shop, AMC Theatres, Ellaola, Keshetbroad; 2 of these — Stop & Shop, AMC — were actually **mis**-inferred as "Business" and got corrected to Groceries/Entertainment in the process). Also removed a second, separate call to the same correction method inside Plaid sync (`_sync_item`) that would have thrown `AttributeError` on the next sync if missed.
  3. Centralized `needs_review` threshold logic (5 independently-duplicated, drifted inline formulas) into one `compute_needs_review()` helper.
  4. Added non-blocking overlap/duplicate warnings at rule-creation time, plus a one-time audit of all 532 active rules — found 20 overlapping pairs, logged as B9.
  5. Scoped `_reapply_rules()` to the triggering rule's own pattern instead of a full-table rescan on every rule create/update (previously confirmed to touch unrelated transactions as a side effect even from a throwaway rule); added a `dry_run` flag as permanent tooling; also wired a reapply into `create_rule_from_transaction`, which previously didn't retroactively catch backlog matches at all.
  6. **Course-corrected mid-implementation**: the original plan called for collapsing the two-pass rule matcher into one pass. A dry-run diff against all 2140 real transactions showed that would silently un-categorize ~387 of them — about a quarter of the rule set relies on a genuine two-stage "normalize the description, then categorize the normalized name" pattern that a single raw-text-only pass breaks. Kept the two-phase structure (it's load-bearing, not incidental complexity); shipped only the three sub-fixes a dry-run diff confirmed were actually safe (0 unintended differences): Phase-1 first-match-wins made consistent across both action and description (previously action was first-wins, description was last-wins, same loop), Transfer-clears-category centralized into `categorize()` itself (removing a snippet duplicated at 7 call sites — caught because the user correctly pushed back that a credit-card payment shouldn't carry a spend category at all), and deterministic rule ordering via the previously-unused `priority_order` column plus a pattern-length tiebreak (51 rules currently share priority=100 with no defined secondary order).
