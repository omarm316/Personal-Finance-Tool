## ✅ Recently Completed

- **B26 fixed — `/api/cards/earn-summary` 43s → 9s (2026-07-30)** — profiled rather than assumed, which was worth it: the endpoint issued **596 queries totalling 41.3s of SQL**, and because `DATABASE_URL` points at a *remote* Railway Postgres, essentially all of it was ~70ms round-trip latency rather than computation. The backlog's suspected cause (per-account `CardProduct` lookups) was real but only **2.7s of 43s**. Four fixes, in descending order of impact:
  1. **`calc_auto_top_category_points()` issued one query per calendar month** while walking its range — and `_compute_balance_bucket()` calls it with `start_date=2000-01-01` whenever a bucket has no baseline snapshot. So a single auto-top account (Citi Custom Cash) cost **~318 round-trips**, Jan 2000 → today, to compute points for an account with ~2 years of data. That alone was ~24s. Rewritten to one query for the whole range, bucketed by `(year, month)` in Python — months with no activity contribute nothing, so skipping them is equivalent. Deliberately preserved the original's quirk of starting at `start_date.replace(day=1)` (it included transactions earlier in the start month) rather than silently narrowing the window.
  2. **`_compute_ecosystem_balance()` re-queried transactions and snapshots once per *person bucket*** — and the helper itself runs once per ecosystem, so ~12 ecosystems × ~3 buckets fanned out badly. Every per-bucket filter is on `spender`/`card_id`/date, all trivially evaluable in Python, so both are now fetched once per ecosystem and partitioned in memory. **Subtle trap handled**: `Transaction.date` is a `timestamp` but `snapshot_date` is a `date` — comparing them directly in Python is a `TypeError`, and truncating `t.date` to a date would silently drop same-day-after-midnight transactions the SQL counted. Uses `datetime.combine(baseline, time.min)` to match SQL's coercion exactly.
  3. **The five per-ecosystem ledger queries** (redemptions, transfers out/in, adjustments, person-transfers) plus a snapshot-people query and a per-ecosystem `Card` lookup — 6+ round-trips per ecosystem — are now one batched `IN` query each, grouped in Python. The `Card` lookup needed no query at all; `card_by_acct` was already in scope.
  4. **The per-account `CardProduct` N+1** the backlog originally identified — batched into one `IN` query via a new `_load_products_by_id()` helper. The same pattern existed in **three** handlers (`cards_earn_summary`, `cash_back_earn_detail`, `ecosystem_earn_detail`), all fixed.
  - **Correctness proven by diff, not by inspection**: captured the full JSON response for all three periods (`mtd`/`qtd`/`ytd`) plus six ecosystem drill-downs, `git stash`ed the changes, captured the same battery from the original code, and diffed recursively. **Zero differences.** The battery itself went 130.3s → 27.5s, confirming `ecosystem_earn_detail` benefits too (shared helper). Profiled result: **596 queries → 121, 42.2s → 9.3s.**

- **🔴 Mobile scrolling was completely broken in portrait — app-wide (2026-07-30)** — Omer, mid-session: "scrolling does not work on my iphone, only when i rotate it to landscape." Not a Dashboard bug; **every page** was affected. Root cause: the `@media (max-width:768px)` block sets `.app-container { flex-direction: column }`, which makes height the main axis. `.main` had `min-width:0` (the fix for the row axis) but **not** `min-height:0`, and its `overflow` is `visible`, so its automatic minimum size (`min-height:auto`) resolved to its full content height — it grew straight past `.app-container`'s fixed `height:100%`. `.content`'s `flex:1` then resolved against that inflated height, so the scroll container ended up exactly as tall as its own content (`scrollHeight === clientHeight`) and could never scroll, with the excess clipped by `.app-container`'s `overflow:hidden`. Landscape is >768px, stays `row`, and was unaffected — which is exactly why it only ever reproduced in portrait. Note `.content` itself was fine all along: `overflow-y:auto` zeroes an item's automatic minimum size, which is why the same latent flaw never bit on the row axis. **One-line fix**: `min-height: 0` on `.main`. Measured before/after at 375×812: `.main` 1412px → 812px, `.app-container` scrollHeight 1412 (600px clipped and unreachable) → 812 (nothing clipped), `.content` scrollHeight 1348/clientHeight 1348 → 1096/748, and a programmatic `scrollTop=400` that previously went nowhere now lands at the true max of 348.
