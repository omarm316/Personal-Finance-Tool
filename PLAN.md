### Points ledger: starting balance, adjustments, full breakdown (2026-07-24, Ecosystems)
Omer wanted to fully reconcile an ecosystem's points balance without hunting down small diffs transaction-by-transaction: an editable starting balance (with its date), and a manual +/- adjustment for drift not worth tracing. Both build on infrastructure already in place from the 2026-07-20 balance-snapshot feature (`PointsBalanceSnapshot`, most-recent-wins baseline in `ecosystem_earn_detail()`).
- **Starting Balance = the earliest snapshot** — no new concept, just full CRUD (added the missing `PATCH`) and a real list UI. The most-recent-snapshot-anchors-the-baseline logic is untouched; "Starting Balance" (earliest) and "the current anchor" (most recent) are just two labels over the same chronological list. Any snapshot after the earliest shows as a "Correction," same list-with-Edit/Delete pattern as Redemptions.
- **New `PointsAdjustment` model** — a dated, signed +/- delta with a description, full CRUD, mirrors `Redemption` exactly. Unlike a snapshot (resets the baseline, erases what came before), an adjustment nudges the running total from its date forward without touching history.
- **`ecosystem_earn_detail()` now returns a `balance_breakdown`** (`starting_balance`, `earned_since_baseline`, `redeemed_since_baseline`, `transferred_out/in_since_baseline`, `adjusted_since_baseline`) instead of just the final `current_balance` — these were already computed as locals, just never exposed. The "Current Balance" widget became a full **Balance Ledger** card showing the whole chain, so a discrepancy is visible at a glance.
- Verified live against Hilton Honors: set a $50,000 starting balance (2025-01-01) → current balance correctly became $144,219; added a real $-230 adjustment via the UI → balance moved to exactly $143,989; edited/deleted both, confirmed round-trip back to the original $94,219 baseline (all test data, cleaned up after — this ecosystem's real starting balance wasn't actually known, unlike the two real challenge fixes from the prior session).
- Small gap found and fixed during verification: the Starting Balance row only had Edit, no way to remove it back to "unset" — added a Remove button matching the Corrections list's existing Edit/Delete pattern.

### Dashboard — Spending Trend chart + Budget Performance bars fixed (2026-07-20, v2.html only)
Two real data-viz bugs found and fixed in `v2.html`'s `DashboardPage`, confirmed live at `/v2` against real production data:
- **Spending Trend line chart**: was using Catmull-Rom smoothing over 6 monthly points, which overshoots past the actual values (visible as a "bulge" between months that doesn't correspond to real data). Replaced with monotone cubic (Fritsch-Carlson) interpolation, which stays smooth but is mathematically constrained to never rise/fall past its two neighboring points. Also added always-on direct value labels per point (swapped for the hover tooltip only when that point is actively hovered) — with only 6 points, reading exact values shouldn't require hovering each dot.
- **Budget Performance table** (`BudgetAndSpendingCard`'s `RowEl`): bar width was `Math.min(actual/budget*100, 100)` — capped at each row's own budget, so *any* category ≥100% of budget rendered as an identical, fully-filled bar (confirmed live: Travel at 458% over and Total at 108% over were visually indistinguishable), and categories with **no budget set at all** got the same alarm-red treatment as ones blown 4-5x over. Fixed by scaling every bar to one shared scale across all visible categories (`scaleMax`, computed from the max actual/budget in view) and rendering the budget threshold as a tick mark instead of the value the bar is normalized against. Added a distinct neutral/muted "no budget set" state (previously indistinguishable from "over budget") and a small legend explaining the four states. Verified against real data — Travel ($2,292, 458% over) and Groceries ($3,724, 310% over) are now visibly different bar lengths, and $0-budget categories (Electronics, Fees & Interest, For Others, Other) render as muted gray with a "no budget" label instead of false-alarm red.

Design direction was worked out first as two published Artifact mockups (before/after comparisons) — an initial pass mistakenly targeted `frontend.html`'s v1 gold/dark theme, corrected after Omer flagged that v2 is the target for all pages going forward; the second mockup and the actual implementation both use v2's real tokens (glass `.card`, blue palette, Outfit/Plus Jakarta Sans), verified against the live `/v2` render before building.

**Not ported to `frontend.html`** — v1 has the identical two bugs (same `smoothPath`/Catmull-Rom, same capped-bar `RowEl` in `BudgetAndSpendingCard`), but since v2 is the going-forward target, this session only touched `v2.html`. If v1 stays live for a while longer, the same fix would need porting separately.

**Found but not fixed, logged for later**: `v2.html` references `var(--violet)`/`var(--violet-soft)`/`var(--violet-border)` in a few places (e.g. the challenge-bonus panel around line 5587) but never defines these as actual CSS custom properties — they silently resolve to nothing. That last change immediately found B7 (already known) plus a second undocumented bad rule and 5 more rules with 100% rejection — logged as B8, needs a human pass since each needs its own judgment call.

**Important operational note surfaced this session**: the local dev server (`.claude/launch.json` → `main.py`) connects to the real production Postgres via `.env`'s `DATABASE_URL` — there is no separate local/test database. Creating any `CategorizationRule` via the API unconditionally triggers `_reapply_rules(force_unlock=True)`, which rescans every transaction against every active rule. A throwaway test-only rule (guaranteed-unmatchable pattern) still caused a real reapply pass that updated 29 and unlocked 8 transactions — those changes are very likely benign (documented, pre-existing, unconditional behavior; the fix landed this session makes that path safer, not riskier) but couldn't be forensically verified since neither `updated_at` nor an audit log is populated by that code path. **Future sessions: assume any local-server action that mutates data is a real production mutation. Prefer read-only verification (curl a GET, inspect via SQL) over exercising POST/PATCH paths live, even for "safe-looking" tests.**

### Classification-engine consolidation — implemented (2026-07-18, same session continued)
Everything flagged as "not addressed" above was addressed later the same session, via a formally planned, dry-run-gated implementation. Full plan (context, sequence, verification methodology) is at `/Users/omermorashti/.claude/plans/shiny-zooming-conway.md` — worth reading in full if picking this back up, since it documents the reasoning behind each decision, not just the outcome. Summary of what shipped, in order (each its own commit, verified against live production data before the next):

1. **Deleted `MerchantOverride`** (model, 3 endpoints, `save_override()`, its lookup step in `enrich_transaction()`) — confirmed 0 rows and no frontend caller before removing. `git d237a4b`.
2. **Deleted `learn_from_corrections()`/`_check_transfer_correction()` entirely**, not just patched. Ran a read-only diff first (`categorize()` with/without corrections enabled) across all non-manually-categorized transactions: 97 depended on them. Reviewed each affected merchant with the user and created 5 explicit rules to replace the inference *before* deleting it — Pruplazacafe, Stop & Shop, AMC Theatres, Ellaola, Keshetbroad. Two of these were a genuine catch, not just backfill: Stop & Shop and AMC Theatres had been silently mis-inferred as category "Business" (low-confidence, 2-3 corrections) — corrected to Groceries/Entertainment during this pass, confirmed with the user rather than assumed. Also found and removed a *second*, separate call to `_check_transfer_correction()` living directly inside Plaid sync's `_sync_item` (not routed through `categorize()`) — deleting the method without catching this would have broken the next real Plaid sync. `git 8fe1ea5`.
3. **Centralized `needs_review`** into `compute_needs_review()`, replacing 5 independently-duplicated, drifted inline formulas. `git c9910b8`.
4. **Rule overlap/duplicate warnings** at creation time (non-blocking), plus a one-time read-only audit of all 532 active rules — 20 overlapping pairs found, logged as BACKLOG B9. `git 89aa432`.
5. **Scoped `_reapply_rules()`** to the triggering rule's own pattern instead of a full-table rescan on every create/update (this is what caused the "throwaway test rule touched 8 unrelated transactions" incident logged below) — both the locked and unlocked branches, plus `update_rule` (previously fully unscoped) and `create_rule_from_transaction` (previously didn't reapply *at all*, so closing a review by creating a rule never retroactively caught other backlog matches). Added a `dry_run` flag as permanent tooling. Validated the scoping recalls every real match with zero misses across 15 sampled rules before trusting it. `git 4a6fcde`.
6. **`categorize()` itself** — this is where the plan changed mid-flight. The original design called for collapsing the two-pass matcher (action/description rules, then category rules) into one unified pass. A dry-run diff against all 2140 real transactions caught this before it shipped: it would have silently un-categorized ~387 of them. Root cause: about a quarter of the real rule set relies on a genuine two-stage pattern — one rule normalizes raw bank text into a clean display name, a *separate* rule then matches that normalized name (not the raw text) to assign a category. A single pass checking only raw/cleaned text breaks that handoff entirely. This is load-bearing rule-authoring convention, not incidental complexity, so the two-phase structure stayed. Landed instead: Phase-1 first-match-wins made consistent for both action and description (previously action was first-wins, description was last-wins in the same loop — an accidental asymmetry, not a design choice); Transfer-clears-category folded directly into `categorize()`, removing a `'' if action=='Transfer' else category` snippet that had been independently duplicated at 7 call sites (the user caught this in conversation — correctly pointed out a credit-card payment shouldn't carry a spend category at all, which is what led to finding the duplication); and deterministic rule ordering via `priority_order` (already existed in the schema for exactly this, never wired into the matcher) plus a pattern-length tiebreak. Re-verified against the actual modified `categorize()` (not just the standalone dry-run replica) before committing: 0 unintended differences across all 2140 transactions. `git 2563818`.

**Explicitly not fixed by this pass** — a "prefer the more specific pattern" reorder was part of the original plan for fixing 8 live "general rule beats specific rule" bugs found in the B9 audit (e.g. generic `UBER` beating specific `UBER EATS`). Tested directly before implementing: it only breaks ties between rules sharing the *exact same* priority number, and the real bugs all involve adjacent-but-different priorities (5233 vs 5234, etc.), so it fixes nothing on real data. Confirmed by re-running the dry-run diff with the change applied — 0 transactions differ. A reorder aggressive enough to actually catch these would risk touching hundreds of unrelated rule pairs unpredictably, so this stayed a manual per-rule priority fix, logged in full in BACKLOG.md B9 (12 pairs total needing a human decision, not just the original 4).

**Deliberately deferred, not started, confirmed with the user**: making LLM enrichment automatic on ingestion (replacing the manual "AI Enrich" button). Separable scope with its own API-cost/behavior tradeoffs — worth its own decision once the real review-queue size after this pass is visible, rather than bundling it into a matching-engine consolidation.

**Operational note reconfirmed this session**: the local dev server has no separate test database — it connects straight to production Postgres. A throwaway test-only rule created purely to verify a code path didn't crash still triggered a real reapply pass touching 8 unrelated transactions as a side effect (this predates and is unrelated to the redesign; it's pre-existing, unconditional `_reapply_rules` behavior that step 5 above specifically fixed). ## Architecture Notes

### Stack
- **Backend**: FastAPI (main.py) + SQLAlchemy + SQLite
- **Frontend**: Single-file React (frontend.html) with inline JSX via Babel
- **Deployment**: Railway (auto-deploys from GitHub on push to main)
- **Data**: Plaid for bank sync, manual import via CSV

### Key Patterns
- `refreshKey` prop pattern (not `key={}`) to reload data without destroying component state
- Credit-netting: `Category.category_type.in_(['expense', 'both'])` for refund detection
- `fmtAcctType()` helper for consistent account type display
- `MultiSelectFilter` reusable component for checkbox-based multi-select dropdowns
- `_challenge_spend_for_card()` for per-card challenge spend tracking
- Modals: never close on backdrop click or Escape — only explicit buttons

### Theme
- **Dark**: Midnight luxury — `#0c0c10` bg, `#d4a44a` gold accent
- **Fonts**: DM Sans (300/400/500) + Playfair Display (400/600 for logo)
- **CSS**: `[data-theme="dark"]` / `[data-theme="light"]` with CSS variables
