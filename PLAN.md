## Session 2026-07-26 — Accounts screen: "add account to an existing bank" flow

Trigger: Omer opened a few new checking accounts and asked how to wire them into the app. Found the app already had the right backend primitive (`GET /api/plaid/update-link-token/{item_id}` + `POST /api/plaid/update-complete/{item_id}` — Plaid Link in update mode against an existing item's access_token, no duplicate bank connection) but the only UI entry point to it (`openReconnect` in `BankRow`, `v2.html`) was gated behind `item.last_error_code==='ITEM_LOGIN_REQUIRED'` — pure error-recovery, no way to reach it from a healthy connection.

**Shipped (part 1)**: added a "+ Add Account" button next to the existing "↺ Sync" button on every healthy (`is_active && !last_error_code`) row in Settings → Bank Links (`v2.html`, `BankRow`) — reuses `openReconnect` as-is, no backend changes at this point.

**Found via real-world test**: Omer tried it against Citibank — Plaid Link opened and completed, but no new accounts/transactions showed up. Root-caused to two separate, previously-latent bugs in the update-mode code path (never exercised before, since there was no UI button to reach it outside error-recovery):
1. `plaid_integration.py: PlaidClient.create_link_token()` never set Plaid's `update.account_selection_enabled` on the update-mode link token request — without it, Plaid's update-mode Link only re-verifies the *already-linked* accounts' credentials and never offers newly-available accounts for selection at all. Fixed: pass `LinkTokenCreateRequestUpdate(account_selection_enabled=True)`.
2. Even if an account were selected, `main.py: plaid_update_complete()` called `_sync_item_background(item_id, clear_cursor=False)` — but the account-discovery/creation block (new `Account` rows for accounts Plaid returns that don't exist in the DB yet) only runs when `clear_cursor=True`. With `False`, a newly-selected account never gets an `Account` row, and `_sync_item` silently skips every transaction with no matching `account_id` (main.py, the `if not account:` branch) — so nothing would ever appear even with bug 1 fixed. Fixed: `plaid_update_complete` now calls with `clear_cursor=True`.
- Bumped the frontend's post-link refresh delay 10s→15s to match the other `clear_cursor=True` flows (force-resync), since this now does a fuller resync.
- Verified bug 1's fix directly against the real Citibank access_token (bypassing the unrelated `redirect_uri must use HTTPS` error, which is a pre-existing local-http-dev-only limitation — Railway's HTTPS deploy doesn't have this problem): `create_link_token(access_token=..., update=LinkTokenCreateRequestUpdate(account_selection_enabled=True))` succeeds and returns a real link token. Could not verify bug 2's fix end-to-end without actually re-running Plaid Link with real credentials (Omer's to do).

**Not done / next step for Omer**: once deployed, retry "+ Add Account" on the Citibank connection(s) — Plaid should now show the new checking accounts for selection, and the post-link sync should create their `Account` rows and pull transactions. ## Session 2026-07-25 (cont'd) — Card product changes with locked, point-in-time points

Trigger: two real Marriott Bonvoy Boundless cards were product-changed to Ritz-Carlton by the issuer, and the app had no way to reflect a product change at all — `POST /api/accounts/{id}/link-product` is a bare overwrite with zero history, reachable in the UI only for never-linked accounts.

Design constraint from Omer, after weighing full retroactive per-transaction date-resolution against a cheaper "current product only" approach: **"once a transaction posts, the points should lock and not dynamically compute"** — a middle ground between the two, without literally severing the account from its history as first floated.

**Shipped:**
- `CardProductHistory` (`database.py`) — effective-dated log per card, mirrors the existing `TransferRatio` pattern (`effective_from`/`effective_to`, `NULL` = current).
- `Transaction` gained `points_earned`, `points_earn_classification`, `points_earn_rate`, `points_product_id`, `points_locked_at` (`database.py`) — computed once and frozen; nothing reads live `compute_points_earn()` on the read path anymore.
- `main.py`: `_resolve_product_for_date()`, `_build_product_rate_maps()` (refactored out of `_build_points_lookup()`), `_lock_points_for_transaction()` — the one write-time locking path, wired into Plaid sync (new + modified + removed txns), CSV/OFX import, manual transaction create, and `update_transaction`/`batch_update_transactions` (re-locks using whichever product was active *on the transaction's own date* whenever category/action/is_excluded/points_earn_override changes).
- All ~8 former live-compute read sites (`_serialize_txn`, ecosystem/portfolio earn rollups, `account_card_detail`, `account_transactions`) now just read the locked columns — net deletion of code at each site.
- `POST /api/cards/{card_id}/change-product` + `GET /api/cards/{card_id}/product-history` — the actual "change product" action (bootstraps history on first use, closes old row, opens new, dual-writes `account.product_id`/`card.product_id` same as `link-product`). Never touches existing `Transaction` rows.
- One-time startup backfill (`_backfill_product_history_and_locked_points`, called from `startup_event`) — bootstraps one history row per already-linked card and locks every pre-existing transaction using today's product (best available truth). Rewritten once already after the first version did per-transaction queries and was clocked at 20-30+ min against the remote Railway Postgres; the shipped version precomputes all rate maps once and iterates in pure Python (ran in ~3 minutes for 2,199 transactions, mostly the final commit's per-row UPDATE flush).
- Frontend (`v2.html`, `AccountCardDetailPage`): "Card Product" header block with current product name + Change Product button + modal (product picker, effective date) + collapsible product-history list.

**Verified live** against the real Bonvoy Brilliant 1000 card (temporarily switched to Amex Platinum and back): old transactions' locked points were untouched by the switch, a new transaction dated after the switch picked up the new product's rate, editing an old (pre-switch) transaction's category re-locked it against the *old* product (not current) — confirmed the whole point of the design. Test transaction and the temporary product-history rows were cleaned up afterward; only the real schema/backfill state remains.

**Discovered mid-session, unresolved and worth a heads-up**: before starting, the production DB already had this exact schema (table + 5 columns, 0 rows) despite no server having run it — traced to a concurrent Claude Code session active in the same directory (confirmed via two unattributed git commits, one of which explicitly deferred "the actual product-change modeling" to this session). Asked Omer, who confirmed it was expected/his doing; proceeded. Underlying concurrent-session risk (same non-worktree-isolated directory, shared production DB) is still open — see `feedback_workflow.md`.

**Not done yet**: the two real Boundless→Ritz-Carlton migrations themselves — blocked on a Ritz-Carlton `CardProduct` not existing in the catalog yet (the other session's card-art commit only swapped the image asset on the existing `marriott_bonvoy_boundless` product_key as a stopgap). Needs a real Ritz-Carlton product added to the catalog before `change-product` can be run for real on those two cards.

### Classification-engine consolidation — implemented (2026-07-18, same session continued)
Everything flagged as "not addressed" above was addressed later the same session, via a formally planned, dry-run-gated implementation. Full plan (context, sequence, verification methodology) is at `/Users/omermorashti/.claude/plans/shiny-zooming-conway.md` — worth reading in full if picking this back up, since it documents the reasoning behind each decision, not just the outcome. Summary of what shipped, in order (each its own commit, verified against live production data before the next):

1. **Deleted `MerchantOverride`** (model, 3 endpoints, `save_override()`, its lookup step in `enrich_transaction()`) — confirmed 0 rows and no frontend caller before removing. `git d237a4b`.
2. **Deleted `learn_from_corrections()`/`_check_transfer_correction()` entirely**, not just patched. Ran a read-only diff first (`categorize()` with/without corrections enabled) across all non-manually-categorized transactions: 97 depended on them. Reviewed each affected merchant with the user and created 5 explicit rules to replace the inference *before* deleting it — Pruplazacafe, Stop & Shop, AMC Theatres, Ellaola, Keshetbroad. Two of these were a genuine catch, not just backfill: Stop & Shop and AMC Theatres had been silently mis-inferred as category "Business" (low-confidence, 2-3 corrections) — corrected to Groceries/Entertainment during this pass, confirmed with the user rather than assumed. Also found and removed a *second*, separate call to `_check_transfer_correction()` living directly inside Plaid sync's `_sync_item` (not routed through `categorize()`) — deleting the method without catching this would have broken the next real Plaid sync. `git 8fe1ea5`.
3. **Centralized `needs_review`** into `compute_needs_review()`, replacing 5 independently-duplicated, drifted inline formulas. `git c9910b8`.
4. **Rule overlap/duplicate warnings** at creation time (non-blocking), plus a one-time read-only audit of all 532 active rules — 20 overlapping pairs found, logged as BACKLOG B9. `git 89aa432`.
5. **Scoped `_reapply_rules()`** to the triggering rule's own pattern instead of a full-table rescan on every create/update (this is what caused the "throwaway test rule touched 8 unrelated transactions" incident logged below) — both the locked and unlocked branches, plus `update_rule` (previously fully unscoped) and `create_rule_from_transaction` (previously didn't reapply *at all*, so closing a review by creating a rule never retroactively caught other backlog matches). Added a `dry_run` flag as permanent tooling. Validated the scoping recalls every real match with zero misses across 15 sampled rules before trusting it. `git 4a6fcde`.
6. **`categorize()` itself** — this is where the plan changed mid-flight. The original design called for collapsing the two-pass matcher (action/description rules, then category rules) into one unified pass. A dry-run diff against all 2140 real transactions caught this before it shipped: it would have silently un-categorized ~387 of them. Root cause: about a quarter of the real rule set relies on a genuine two-stage pattern — one rule normalizes raw bank text into a clean display name, a *separate* rule then matches that normalized name (not the raw text) to assign a category. A single pass checking only raw/cleaned text breaks that handoff entirely. This is load-bearing rule-authoring convention, not incidental complexity, so the two-phase structure stayed. Landed instead: Phase-1 first-match-wins made consistent for both action and description (previously action was first-wins, description was last-wins in the same loop — an accidental asymmetry, not a design choice); Transfer-clears-category folded directly into `categorize()`, removing a `'' if action=='Transfer' else category` snippet that had been independently duplicated at 7 call sites (the user caught this in conversation — correctly pointed out a credit-card payment shouldn't carry a spend category at all, which is what led to finding the duplication); and deterministic rule ordering via `priority_order` (already existed in the schema for exactly this, never wired into the matcher) plus a pattern-length tiebreak. Re-verified against the actual modified `categorize()` (not just the standalone dry-run replica) before committing: 0 unintended differences across all 2140 transactions. `git 2563818`.

**Explicitly not fixed by this pass** — a "prefer the more specific pattern" reorder was part of the original plan for fixing 8 live "general rule beats specific rule" bugs found in the B9 audit (e.g. generic `UBER` beating specific `UBER EATS`). Tested directly before implementing: it only breaks ties between rules sharing the *exact same* priority number, and the real bugs all involve adjacent-but-different priorities (5233 vs 5234, etc.), so it fixes nothing on real data. Confirmed by re-running the dry-run diff with the change applied — 0 transactions differ. A reorder aggressive enough to actually catch these would risk touching hundreds of unrelated rule pairs unpredictably, so this stayed a manual per-rule priority fix, logged in full in BACKLOG.md B9 (12 pairs total needing a human decision, not just the original 4).

**Deliberately deferred, not started, confirmed with the user**: making LLM enrichment automatic on ingestion (replacing the manual "AI Enrich" button). Separable scope with its own API-cost/behavior tradeoffs — worth its own decision once the real review-queue size after this pass is visible, rather than bundling it into a matching-engine consolidation.

**Operational note reconfirmed this session**: the local dev server has no separate test database — it connects straight to production Postgres. A throwaway test-only rule created purely to verify a code path didn't crash still triggered a real reapply pass touching 8 unrelated transactions as a side effect (this predates and is unrelated to the redesign; it's pre-existing, unconditional `_reapply_rules` behavior that step 5 above specifically fixed). Every write-path test in this implementation was done deliberately with that in mind — dry-run/read-only verification was preferred throughout, and is now built into the app itself (`_reapply_rules`'s `dry_run` flag) as permanent tooling for future sessions facing the same constraint.

## Architecture Notes

### Stack
- **Backend**: FastAPI (main.py) + SQLAlchemy + SQLite
- **Frontend**: Single-file React (frontend.html) with inline JSX via Babel
- **Deployment**: Railway (auto-deploys from GitHub on push to main)
- **Data**: Plaid for bank sync, manual import via CSV

### Key Patterns
- `refreshKey` prop pattern (not `key={}`) to reload data without destroying component state
- Credit-netting: `Category.category_type.in_(['expense', 'both'])` for refund detection
- `fmtAcctType()` helper for consistent account type display
- `MultiSelectFilter` reusable component for checkbox-based multi-select dropdowns
- `_challenge_spend_for_card()` for per-card challenge spend tracking
- Modals: never close on backdrop click or Escape — only explicit buttons

### Theme
- **Dark**: Midnight luxury — `#0c0c10` bg, `#d4a44a` gold accent
- **Fonts**: DM Sans (300/400/500) + Playfair Display (400/600 for logo)
- **CSS**: `[data-theme="dark"]` / `[data-theme="light"]` with CSS variables
